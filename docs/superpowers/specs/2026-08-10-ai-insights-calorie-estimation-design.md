# Habit 0.6.0 AI 洞察、图片热量估算与饮食详情设计规格

日期：2026-08-10  
目标版本：0.6.0（`versionCode = 12`）  
基线版本：0.5.1（`versionCode = 11`、Room 4、备份 schema 4）

## 1. 背景与目标

Habit 已形成“人生工作台”结构，习惯打卡和饮食记录是两个平级模块。0.5.1 已完成饮食阅读、分类、统计、照片预览、备份和全局 UI 一致性。本次迭代建立可复用的 AI 基础能力，并交付两个首批功能：

1. 基于习惯与饮食结构化数据生成 AI 综合周报；
2. 根据用户主动选择的餐食照片估算热量，由用户确认后写入；
3. 精细化饮食详情，使照片、记录内容、AI 依据与最终采用值具有清晰层级；
4. 支持配置多个 OpenAI 兼容模型，并将不同 AI 功能绑定到指定模型；
5. 保留 0.5.1 本地数据、旧备份兼容性与现有稳定签名。

本版本的 AI 是可选增强功能。未配置模型、断网、服务异常或 AI 输出无效时，习惯、饮食、统计、分类和备份必须继续正常工作。

## 2. 已确认范围

### 2.1 本版本包含

- 多模型配置管理；
- 模型文本/图片能力声明与连接测试；
- “综合周报”和“图片热量估算”的功能绑定；
- 用户主动生成上一完整自然周的综合周报；
- 周报预览、保存、按周替换与历史查看；
- 餐食照片热量估算、结果确认、人工修正与依据保存；
- 精细化餐食和饮品详情页；
- AI 非敏感配置、功能绑定、周报和热量依据备份；
- API Key 的 Android Keystore 加密存储；
- Room 4 → 5 显式无损迁移；
- 备份 schema 4 → 5 向前兼容升级。

### 2.2 本版本不包含

- AI 对话或围绕周报继续追问；
- 后台自动生成周报、定时任务或推送通知；
- 自动调用 AI、静默重试或静默切换备用模型；
- 登录、云同步、统一后台、支付或代付 API 费用；
- 上传饮食备注、习惯备注或周报以外的历史原始数据；
- 使用图片生成周报；
- 自动覆盖用户已填写的餐食名称、食物明细或备注；
- 饮品图片热量估算；首版只对 `MEAL` 餐食开放；
- 本地大模型推理引擎。局域网兼容接口可以配置，但推理由外部服务完成。

## 3. 信息架构与导航

### 3.1 侧滑菜单

在现有“习惯”和“饮食”模块后增加可折叠模块组：

- `✨ AI 洞察`
  - `📝 综合周报`
  - `🤖 模型配置`

所有入口继续使用 Emoji。模块组沿用现有折叠状态和根页面导航规则：点击侧栏根入口时清理旧子页面栈，不恢复之前停留的编辑或详情页。

“主题与设置”不重复放置完整模型管理功能，只可在 AI 未配置提示中提供跳转按钮，避免与侧栏入口重复。

### 3.2 工作台

今日工作台增加“本周洞察”卡：

- 未保存上一周报告：显示上一完整自然周日期范围和“生成周报”；
- 已保存：显示报告标题、生成时间和“查看报告”；
- 未配置绑定模型：显示“先配置 AI 模型”；
- 生成失败：卡片不缓存错误报告，只显示可重试状态。

工作台只消费 AI 周报摘要接口，不直接组织提示词或访问网络。

### 3.3 模型配置页面

页面采用两个居中的滑动页签：

1. `模型配置`；
2. `功能绑定`。

模型页使用统一的“+”悬浮按钮新增模型。每张模型卡显示：

- 自定义名称；
- 模型 ID；
- 文本/图片能力标签；
- HTTPS 或已明确允许 HTTP；
- Key 是否已配置；
- 最近一次测试状态与北京时间。

功能绑定页显示：

- 综合周报 → 具备文本能力的模型；
- 图片热量估算 → 具备图片能力的模型。

绑定选择器只列出能力匹配、未停用且最近一次对应能力测试通过的模型。测试后来失败不自动解除既有绑定，但使用功能时必须提示重新测试或改绑。

## 4. 模型配置

### 4.1 配置字段

每条模型配置包含：

- `externalId`：创建时生成的 UUID，用于备份合并时识别同一配置；
- `name`：用户自定义名称；
- `baseUrl`：OpenAI 兼容接口基础地址；
- `modelId`：请求中的模型 ID；
- `supportsText`：声明支持文本；
- `supportsVision`：声明支持图片；
- `allowInsecureHttp`：用户是否明确允许 HTTP；
- `enabled`：是否启用；
- `lastTestedAt`、`lastTestStatus`、`lastTestMessage`；
- `createdAt`、`updatedAt`。

首版协议固定为 OpenAI Chat Completions 兼容协议。`baseUrl` 可以填写到 `/v1`，客户端规范化后调用 `/chat/completions`。如果用户填写完整 `/chat/completions` 地址，不重复追加路径。

URL 校验规则：

- 仅接受 `https` 和用户明确允许后的 `http`；
- 必须包含主机；
- 拒绝 `file`、`content`、`javascript` 等其他 scheme；
- 拒绝 URL 中包含用户名、密码或片段；
- 移除末尾多余 `/`，但不改写主机和自定义路径。

### 4.2 API Key

API Key 不进入 Room。应用使用 Android Keystore 生成不可导出的 AES/GCM 主密钥，将每个模型的 Key 加密后保存在不参与备份的本地偏好文件中，索引为模型配置 `externalId`。

- UI 只显示“已配置”和末尾 4 位；
- 完整 Key 不可从应用复制或再次显示；
- 替换 Key 覆盖旧密文；
- 修改 API 地址、模型 ID、能力声明或 Key 后，原测试状态立即重置为“未验证”；
- 删除模型同步删除其密文；
- Keystore 失效或密文无法解密时，将该模型标记为“需要重新填写 Key”；
- 请求、响应、异常、崩溃信息和测试报告不得包含 Key 或 `Authorization` 请求头；
- API Key 不进入 JSON/ZIP 备份。

### 4.3 HTTP 风险开关

应用清单需要允许兼容接口的明文连接，但 AI 客户端默认拒绝所有 HTTP URL。只有单条模型配置开启 `allowInsecureHttp` 且用户确认“网络中的其他设备可能读取 API Key 和数据”后，客户端才允许该模型发起 HTTP 请求。

## 5. 连接与能力测试

保存模型前允许测试：

- 文本测试：发送最短结构化请求并验证文本响应；
- 图片测试：仅当声明图片能力时，发送应用内生成的无个人信息测试图；
- 测试结果记录状态、北京时间和去敏后的错误摘要；
- 测试不会保存为周报或热量依据；
- 测试失败可以保存配置，但不能误显示为已验证。

错误提示必须区分：

- 地址格式错误；
- Key 缺失或无效；
- 权限/余额限制；
- 模型不存在；
- 模型不支持图片；
- 网络不可用或超时；
- 服务端响应格式不兼容。

## 6. AI 综合周报

### 6.1 日期范围

周报分析“上一完整自然周”，以北京时间周一 00:00 至周日 23:59:59 为边界。例如 2026-08-10 周一生成时，范围为 2026-08-03 至 2026-08-09。

同一周只保留一份已保存报告。重新生成先展示新预览，用户确认后才替换旧报告。

### 6.2 发送数据

应用先在本地生成紧凑 JSON 摘要，只包含：

习惯：

- 名称和分类名称；
- 本周适用天数；
- 完成天数和完成率；
- 连续完成情况；
- 每日是否完成的布尔序列。

饮食：

- 记录显示名称；
- 餐食/饮品类型、餐次或饮品分类；
- 北京时间的日期和时间段；
- 已填写的最终热量及来源；
- 每日记录数、餐食数、饮品数和已知热量合计；
- 热量覆盖条数，明确区分“缺失”与真实 0 kcal。

明确不发送：

- 饮食照片；
- 饮食备注；
- 数据库 ID、文件路径、API Key；
- `createdAt`、`updatedAt` 等无关审计字段；
- 其他周的明细数据。

若习惯和饮食均无数据，不调用 AI，显示“上一周还没有可分析的记录”。如果只有一个模块有数据，允许生成，但缺失模块必须显示“数据不足”，模型不得补造结论。

### 6.3 返回结构

模型必须返回下列结构：

- `title`：一句周报标题；
- `overview`：本周概览；
- `habitAnalysis`：习惯表现；
- `dietAnalysis`：饮食规律；
- `correlationFinding`：谨慎表达的跨模块观察；
- `suggestions`：恰好 3 条下周可执行建议；
- `cautions`：数据缺失或不能确定的事项。

应用对字段、长度、建议数量和 JSON 类型进行校验。解析失败、字段缺失或内容全空时不保存；不得把原始模型文本直接显示为正式周报。

### 6.4 页面与保存

周报详情沿用已确认的低饱和天蓝、偏白卡片布局，顺序为：

1. 日期范围、标题与本周概览；
2. 本地计算的习惯完成率、饮食记录数、饮食记录天数；
3. 习惯表现；
4. 饮食规律；
5. 关联发现；
6. 三条下周建议；
7. 数据覆盖和 AI 免责声明。

生成结果先处于预览态。用户点击“保存本周报告”后写入本地。历史页按周倒序排列；点击进入只读详情。历史报告不随当前模型配置改名或删除而变化，保存时记录模型名称和模型 ID 快照。

## 7. 图片热量估算

### 7.1 入口与前置条件

入口位于餐食编辑页照片和热量区域，文案为“AI 估算热量”。仅 `DietRecordType.MEAL` 显示。

发起前必须满足：

- 已绑定并启用具备图片能力的模型；
- API Key 可解密；
- 当前草稿至少有 1 张可读照片；
- 用户确认本次发送的照片数量和餐食名称。

当前记录最多 3 张照片，默认全选，用户可以取消部分照片，但至少保留 1 张。

### 7.2 图片处理与发送

客户端在后台线程生成临时分析副本：

- 保留方向正确的像素内容；
- 最长边不超过 1536 px；
- JPEG 质量 82；
- 去除 EXIF 元数据；
- 总编码体积超过 6 MB 时继续降低尺寸或提示减少照片；
- 请求结束后立即删除临时副本；
- 原始私有照片不修改。

除所选照片外，只发送当前餐食名称。备注、历史记录、分类统计和其他照片不发送。

### 7.3 返回结构与校验

模型返回：

- 识别食物列表；
- 每项推测份量；
- 每项最小/最大 kcal；
- 总最小/最大 kcal；
- 建议采用值；
- 影响准确性的简短说明。

校验规则：

- 所有热量必须为非负整数；
- 最小值不得大于最大值；
- 建议值必须位于总区间内；
- 食物列表不能为空；
- 不接受超过合理上限的异常数字；首版单餐总上限为 10000 kcal；
- 输出无效时不改变草稿。

### 7.4 用户确认与写入

估算页显示照片、识别食物、份量、单项区间、总区间、建议值和误差提示。用户可以修改最终采用热量：

- 未修改建议值：`CalorieSource.AI_ESTIMATE`；
- 修改建议值：`CalorieSource.MANUAL`，估算依据记录 `wasModified = true`；
- 点击“采用”只填入最终热量并把估算依据附加到当前草稿；
- 不覆盖餐食名称、用户食物明细和备注；
- 用户仍需在餐食编辑页点击“保存”，才把记录和估算依据写入数据库；
- 取消编辑时不保存估算依据。

餐食记录与估算依据必须在同一 Room 事务中保存。删除餐食时级联删除估算依据；编辑并重新估算时替换上一份依据；仅手动修改热量而未重新估算时保留依据，但详情明确显示最终值已人工修正。

## 8. 精细化饮食详情

### 8.1 通用结构

餐食和饮品详情采用统一阅读层级：

1. 轻量返回箭头、居中“饮食详情”、小号“编辑”；
2. 第一张照片作为主视觉，多图显示 `当前位置 / 总数`，点击打开现有全屏预览；
3. 名称、记录类型、餐次/饮品类型、北京时间和最终热量；
4. 分类、餐次或饮品属性、照片数量的紧凑信息区；
5. 用户记录内容；
6. AI 估算依据（存在时）；
7. 备注；
8. “再记一次”操作。

无照片时不制造大面积空白，使用紧凑默认 Emoji 头图。图片继续采用后台采样解码，不能在主线程解码全尺寸原图。

### 8.2 餐食详情

显示：

- 餐食名称、分类、餐次、日期时间；
- 最终热量及来源；
- 用户食物明细和用户填写的单项热量；
- AI 识别食物、份量、单项区间、总区间、模型名称快照、分析时间；
- “最终采用 X kcal · 未修改/手动修正”；
- 备注。

AI 识别明细与用户食物明细必须是两个独立卡片，不得混合为同一数据来源。

### 8.3 饮品详情

显示：

- 饮品名称、分类、品牌/门店、容量、温度、甜度、加料、杯数和最终热量；
- 现有 `temperature + iceLevel` 兼容展示规则；
- 照片和备注。

饮品首版不显示“AI 估算”入口或空的 AI 卡片。

## 9. 数据模型与数据库迁移

Room 数据库从 4 升级到 5，新增：

### 9.1 `ai_model_configs`

- `id` Long 主键；
- `externalId` UUID String 唯一索引；
- `name`、`baseUrl`、`modelId`；
- `supportsText`、`supportsVision`、`allowInsecureHttp`、`enabled`；
- `lastTestedAt` nullable；
- `lastTestStatus`、`lastTestMessage`；
- `createdAt`、`updatedAt`。

表中不包含 API Key、密文或 Key 末尾字符。

### 9.2 `ai_feature_bindings`

- `feature` String 主键；
- `modelConfigId` nullable；
- `updatedAt`。

功能枚举首版只有 `WEEKLY_REPORT` 和 `MEAL_CALORIE_ESTIMATE`。模型删除时将相关绑定置空，并在删除确认框列出受影响功能。

### 9.3 `ai_weekly_reports`

- `id` Long 主键；
- `startEpochDay`、`endEpochDay`，组合唯一；
- `generatedAt`；
- `modelNameSnapshot`、`modelIdSnapshot`；
- `title`、`overview`、`habitAnalysis`、`dietAnalysis`、`correlationFinding`；
- `suggestionsJson`、`cautionsJson`、`coverageJson`；
- `createdAt`、`updatedAt`。

### 9.4 `ai_calorie_estimates`

- `mealRecordId` 主键和外键，删除餐食时级联；
- `generatedAt`；
- `modelNameSnapshot`、`modelIdSnapshot`；
- `itemsJson`；
- `totalMinKcal`、`totalMaxKcal`、`suggestedKcal`、`adoptedKcal`；
- `wasModified`；
- `accuracyNote`。

`MIGRATION_4_5` 只创建新表和索引，不修改、删除或重写现有表。迁移后的旧记录没有 AI 依据，正常按原样显示。

## 10. 备份 schema 5

备份新增：

- `aiModelConfigs`：不含 API Key；
- `aiFeatureBindings`；
- `aiWeeklyReports`；
- `aiCalorieEstimates`。

导入规则：

- schema 1–4 缺少 AI 字段时按空列表处理；
- schema 5 的模型配置导入后统一显示“需要重新填写 Key”；
- 合并导入模型配置以 `externalId` 识别同一配置，按 `updatedAt` 使用较新数据，并重映射功能绑定；不同 `externalId` 即使 Long ID 冲突也必须作为两条配置导入；
- 同一自然周报告按 `updatedAt` 使用较新数据；
- 热量依据随餐食 ID 重映射，冲突时使用较新的饮食记录及其依据；
- 若模型配置不存在或未导入，对应功能绑定置空；
- API Key、请求原文和临时压缩照片永不进入 ZIP；
- 任何被本次导入新增或更新的模型配置都清除本机同 `externalId` 的旧 Key，并重置为“需要重新填写 Key”，防止旧 Key 被发送到导入后改变的地址；未被导入触及的本机配置和 Key 保持不变；
- 完全替换导入前清理全部旧模型 Key 密文，避免旧 Key 被导入配置的 `externalId` 意外引用。

备份预览增加模型配置数、周报数和 AI 热量依据数，不宣称包含 API Key。

## 11. 网络、分层与组件边界

新增网络权限 `android.permission.INTERNET`。网络实现使用一个稳定、可测试的 HTTP 客户端，并保持如下边界：

- `AiSecretStore`：只负责 Key 加密、读取和删除；
- `AiModelRepository`：模型非敏感配置和功能绑定；
- `AiCompletionClient`：OpenAI 兼容请求、超时、状态码映射和去敏；
- `WeeklyReportPromptBuilder`：把本地统计映射为严格输入，不访问网络；
- `WeeklyReportParser`：校验结构并生成领域模型；
- `CalorieEstimateImagePreparer`：后台生成无 EXIF 临时副本；
- `CalorieEstimateParser`：校验食物、区间和建议值；
- `AiWeeklyReportRepository`、`AiCalorieEstimateRepository`：Room 持久化；
- ViewModel 只编排状态，不拼接 HTTP JSON、不直接处理密钥或 Bitmap。

HTTP 客户端统一设置连接、读取和总请求超时。取消页面或用户主动取消时取消协程和网络请求。错误对象只暴露分类、中文用户消息和无敏感技术摘要。

## 12. 失败处理与费用控制

- 所有 AI 调用由明确按钮触发；
- 调用前显示将发送的数据类型、日期范围或照片数量；
- 不自动重试，不在启动或后台静默调用；
- 401/403 提示检查 Key 或权限；
- 402/429 提示余额、配额或频率限制；
- 404 提示地址或模型 ID；
- 415/模型错误提示图片能力不支持；
- 5xx 提示服务暂时不可用；
- 超时和离线分别提示；
- 格式无效提示“模型返回内容无法解析，可更换模型或重试”；
- 周报失败不替换旧报告；
- 热量估算失败不改变草稿；
- 不用一个功能的失败状态阻塞另一个功能。

## 13. UI 视觉规范

已确认的预览方向：

- 继续使用偏白背景和低饱和天蓝强调色；
- AI 页面仍是 Habit 工作台卡片风格，不做聊天软件气泡界面；
- 标题、返回、编辑、“+”和 FAB 复用全局轻量组件；

- 所有主要操作触控高度至少 48 dp；

## 15. 验收标准

1. 用户能配置多个模型，并将综合周报和图片热量估算绑定到不同模型。
2. API Key 仅存在于 Keystore 加密存储，不进入 Room、备份、日志或错误提示。
3. 周报只发送上一完整自然周的结构化习惯和饮食数据，不发送照片或备注。
4. 周报按确认结构显示并按周保存历史；失败不会替换旧报告。
5. 用户可主动用 1–3 张餐食照片获得食物明细、热量区间和建议值。
6. AI 建议值只有经用户采用后才写入草稿，仍需保存餐食记录才持久化。
7. 用户修改建议值时正确标记为手动修正，并保留 AI 原始估算依据。
8. 精细化饮食详情明确区分用户记录、AI 依据和最终采用值。
9. 0.5.1 数据和 schema 1–4 备份无损兼容；schema 5 不包含 API Key。
10. 未配置 AI、断网或服务异常不影响习惯、饮食和备份的非 AI 功能。
11. 完整自动化验证通过，0.6.0 release APK 使用稳定签名并可覆盖安装。
